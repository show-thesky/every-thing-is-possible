# pierce

DeepSeek Harness 提示词组装层的**研究性工具**。目的是搞清楚一件事：模型最终读到的
系统提示词与上下文，到底是从哪儿拼出来的，以及"我以为改过了"和"模型实际读到"
差在哪。

## 它做什么

宿主在每次模型调用前会把若干 section 与 context 拼成提示词，其中一部分会变成
用户消息里的运行时快照。这个工具在三个文档化的位置上做观察与实验：

1. `systemPrompt.section()` —— 注册三段 section，观察它们落到系统提示词的什么位置。
2. `system-prompt/assemble` waterfall —— 观察上下文的拼装过程。
3. 包装 `systemPrompt.refreshContext` —— 观察上下文"重读"之后如何变成那条快照。

每次实验都会把改写前后的指纹记进账本。另有一个独立审计器：它读会话日志里
**模型实际收到的文本**（`system/message` 与 `user/message`），按同一套判据逐段检查，
再与账本对账。对不上就是一次"漏"，报出记录序号与通道。

为什么要这么做：改写的正确性不能靠自述。只有把"模型看到的"和"我声称改过的"
放在一起比，才知道覆盖到底成不成立。

## 用

```
node install.mjs --dry-run      # 先看它要做什么
node install.mjs                # 挂进 profile（junction + bundles + link 依赖）
node install.mjs --remove       # 摘掉，并恢复原有条目
node auditor/index.mjs          # 对账：只看本次启动之后
node tests/selftest.mjs         # 29 条自测
```

正文在 `prompts/core.md`，每轮现读磁盘，改完下一轮生效。

## 已知边界

- 只认日志 v4；遇到别的版本直接报错，不猜。
- 只检查 `system/message` 与 `user/message` 两层，`tool/result` 噪声过大。
- 只报告，不自动修补。
- 只在 Windows 桌面版上验证过。
